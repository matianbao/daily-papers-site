1. Shape Your Feed: An LLM-based Agentic System for Conversational Recommendation

  • 作者: Ziyun Xu, Bosen Ding, Yue Zhang, Ji Qi, Qingyuan Song, Jizhou Huang, Liwei Wang, Jeffrey Santelli, Yue Weng, Qichao Que, Zhenheng Yang, Junfeng Pan, Linhong Zhu

  • 机构: panjunfeng@meta.com, qsong@meta.com , zhangyue@meta.com , jsantelli@meta.com , bosending@meta.com , yweng@meta.com , Meta Platforms, jacksonhuang@meta.com , linhongzhu@meta.com , qichao@meta.com , panjunfeng@meta.com , zhenheny@meta.com , jiqi@meta.com , liweiw@meta.com , Meta PlatformsMenlo ParkCaliforniaUSA, vincentxu@meta.com

  • 链接: arXiv | PDF

  • 来源: 📄 arXiv 关键词检索
  • 核心方法: 把工业推荐系统从 被动ranking 范式（靠 click/dwell 隐式信号猜偏好）升级成对话式主动 steering：用户用自然语言直接表达「我想看更多X、少看Y」，一个 LLM-based agentic 系统实时改写 feed。训练上用了 SFT + DPO 组合，作者代号 SYF（Shape Your Feed）。
  • 对比方法/Baselines: 对标传统 implicit-feedback 深度推荐（Hu et al. 2008 的 WMF、Rendle 的 BPR），以及各类 conversational recommendation 系统。
  • 借鉴意义: 这是你的核心战场。被动 ranking 的天花板是「用户没法主动 steer」，Meta 直接上 agent 让用户开口说话——如果这套能规模化，对现有 CTR/ranking 全家桶是范式冲击。至少值得研究它怎么把自然语言意图落到 feed 排序上。
  • 锐评: Meta 亲自下场做对话式推荐，signal 很强。但要泼冷水：demo 里「用户主动表达偏好」的假设在真实场景多脆弱——绝大多数用户就是懒得开口，被动信号之所以主流不是因为技术不行，是因为它不需要用户动嘴。这套系统的天花板取决于「愿意 steer 的用户占比」，摘要没给这个数。方法本身（SFT+DPO+agent 编排）没有新东西，赢在场景和数据。👀

2. IB-RL: Isolated Bilateral Reinforcement Learning for Strategic Dialogue Agents

  • 作者: Senhao Wang\equalcontrib
  • 机构: Dcar Inc. ByteDance, huangmingxing.1024, wangxingguang.123, chengyi.2024, liwenhao.6@bytedance.com
  • 链接: arXiv | PDF
  • 来源: 📄 arXiv 关键词检索
  • 核心方法: 字节 Dcar 团队的电销砍价 agent。提出 IB-RL（Isolated Bilateral RL）：把「非平稳、会策略性对抗的对手」这一难点隔离处理，双边各训一个策略，避免标准 RL 在对抗环境里的训练崩溃。落地在 TeleSales / WeChat 加微场景，用 DeepSeek、GLM-5 做 backbone。
  • 对比方法/Baselines: 对标 stationary-reward 的标准 RL（数学推理、代码那套 verifiable reward），以及 DoND（Deal or No Deal）类砍价 benchmark。
  • 借鉴意义: 广告/转化的正脉。策略性对话（砍价、加微转化）本质是非平稳博弈，标准 RLHF 那套 verifiable reward 直接失效。IB-RL 的「隔离双边」思路对任何 agent-vs-user 的转化场景都有借鉴。
  • 锐评: 真实商业闭环 + 字节数据，这类论文比学术 benchmark 靠谱。核心洞察对：把对手当成会适应的策略体而不是固定环境，这是 RLHF 在对话 agent 上的真实痛点。但「Isolated Bilateral」听起来优雅，实操里两个策略互训极易陷入退化均衡或 mode collapse，摘要没交代怎么稳住。另外电销砍价的伦理味道有点冲。🔥

3. Trajectory-Relative Hindsight Distillation for Agentic Reinforcement Learning

  • 作者: Zheng, Haoyu, Zhu, Yun, Wang, Qing, Zhang, Wenqiao
  • 机构: Work done during internship at Tencent.Corresponding author, 1Zhejiang University, 3Tencent, 2Shanghai AI Laboratory
  • 链接: arXiv | PDF

  • 来源: 📄 arXiv 关键词检索

  • 核心方法: TRIAL（Trajectory-Relative Hindsight Distillation）：agentic RL 里一次完整 rollout 会产生多个 hindsight 信号，但怎么把它们分配到各个 turn 不清楚。TRIAL 提出统一的 turn-aligned scoring 协议，做轨迹相对的 hindsight 蒸馏。基于 GRPO，在 WebShop 等环境验证。

  • 对比方法/Baselines: 对标 group-relative 目标（GRPO），以及各类 hindsight relabeling 方法。
  • 借鉴意义: 多轮 agent 训练的核心难题：sparse outcome reward 怎么摊到每一步。这块做好了，agent 的样本效率能显著提升——对任何需要长 horizon 决策的 agent（包括推荐/广告 agent）都有用。
  • 锐评: 腾讯+浙大出品，切入点扎实。今天光信用分配就撞了四篇，说明这是当前 agentic RL 的兵家必争之地。TRIAL 的「turn-aligned scoring」比朴素均匀分配聪明，但「hindsight 蒸馏」这套依赖 teacher 信号质量——teacher 本身如果 hindsight 就有偏，学生只是学得更快地错。摘要没给和其他三篇撞车工作的直接对比。👀

4. How Much, Then Where: Credit-Conserving Action-to-Token Allocation for Multi-Turn Agent Reinforcement Learning

  • 作者: Lichao Ma1,2,\equalcontrib
  • 机构: Beijing Institute of Technology, Fudan University, Peking University, Tongji University, Tsinghua University, Zhejiang University
  • 链接: arXiv | PDF
  • 来源: 📄 arXiv 关键词检索
  • 核心方法: FACTOR：把多轮 agent RL 的信用分配拆成两层——轨迹级（哪个 action 该拿多少 credit）和 token 级（一个 action 内部怎么分到 token）。用 checkpoint-calibrated TD residual 做 per-action credit（保证 telescope 到轨迹优势），再用 feedback-conditioned 机制做 token 分配。在 ScienceWorld、WebShop 验证。
  • 对比方法/Baselines: 对标 SERL 及各类 outcome-based 均匀分配的 critic-free 方法。
  • 借鉴意义: 「How much, then where」这个分解视角很清晰，比一锅端的 trajectory reward 精细。对训练长 horizon agent 的团队有直接工程价值。
  • 锐评: 六校联署（清北复交同浙），阵容豪华。分解思路是这批信用分配论文里最干净的一个：先定量再定位。TD residual 做 per-action credit 保证 telescoping 是正经数学。但两层分配意味着两处超参和两处误差累积，实操调参地狱可以预见。和 TRIAL、Gated-BEPO 高度同质，得看谁的 benchmark 数字硬。👀

  • 作者: Hongxi Yan1,2, Ziyue Huang3, Shichao Fan1, Qingjie Liu1,2
  • 机构: Beihang University, Beijing, China, Qualcomm, Beijing, China, State Key Laboratory of Virtual Reality Technology and Systems, Zhongguancun Laboratory, Beijing, China
  • 链接: arXiv | PDF

一句话总结

首个大规模实证研究，分析 2,303 个 Agent 上下文文件（CLAUDE.md/AGENTS.md/copilot-instructions.md）的结构、维护模式与指令内容，揭示功能性指令主导而安全/性能等非功能性需求严重缺失的现状。

核心贡献

  1. 首个大规模 Agent 上下文文件实证研究: 收集 1,925 个仓库中的 2,303 个 Agent 上下文文件（ACF），覆盖 Claude Code、OpenAI Codex、GitHub Copilot 三大工具
  2. 16 类指令分类体系: 通过人工标注构建 Agent 上下文文件的指令分类 taxonomy，发现功能性指令（Build and Run 62.3%、Implementation Details 69.9%）远多于非功能性需求（Security 14.5%、Performance 14.5%）
  3. 自动分类可行性验证: 使用 GPT-5 实现 0.79 F1-score 的自动分类，证明大规模监控 Agent 上下文文件的可行性

问题背景

要解决的问题

Agentic Coding 工具（如 Claude Code、OpenAI Codex、GitHub Copilot）依赖 Agent 上下文文件（ACF）来理解项目架构、遵循编码规范、执行构建测试。但目前缺乏关于这些文件结构、演化方式和实际内容的系统性实证证据。

现有方法的局限

  • 官方文档仅提供高层指导（如"描述架构和工作流"），开发者只能通过试错来设计这些文件
  • 已有研究主要关注 LLM 的模型能力、交互模式和即时提示，而非持久化的项目级上下文配置
  • 前序工作 (Chatlatanagulchai et al., 2025) 仅研究了 253 个 Claude Code 文件，范围有限

本文的动机

Agent 上下文文件作为一种新型软件工件（"READMEs for agents"），在 Agentic Coding 生态中扮演关键角色，但学术界对其缺乏基本的经验性认知。本文旨在通过大规模实证分析填补这一空白。

方法详解

研究设计

本文围绕四个研究问题（RQ）展开：

  • RQ1: Agent 上下文文件的特征（大小、可读性、结构）是什么？
  • RQ2: 开发者维护 Agent 上下文文件的频率如何？
  • RQ3: Agent 上下文文件包含哪些指令？
  • RQ4: 能否自动分类 Agent 上下文文件中的指令？

数据收集

数据来源: AIDev 数据集 (Li et al., 2025b)，筛选 GitHub Stars ≥ 5 的 8,370 个仓库

文件检索: 通过 GitHub API 扫描仓库根目录，按官方命名规范检索： - CLAUDE.md → Claude Code（922 个） - AGENTS.md → OpenAI Codex（694 个） - copilot-instructions.md → GitHub Copilot（687 个） - 总计: 2,303 个文件来自 1,925 个仓库

RQ1: 特征分析方法

  • 大小: 正则表达式 \w+ 匹配单词数
  • 可读性: FRE 指标（越高越易读）
  • 结构: 统计 Markdown 标题层级（H1-H5）分布
  • 统计检验: Mann-Whitney U Test + Cliff's Delta 效应量

RQ2: 维护模式分析

  • 提取所有修改 ACF 的 commit 历史
  • 统计 commit 数量、时间间隔、增删行数
  • 总计分析 5,655（Claude Code）+ 2,767（Codex）+ 2,237（Copilot）= 10,659 次 commit

RQ3: 内容分类方法

两阶段人工标注:

  1. 标签创建阶段: 提取 H1/H2 标题 → 3 个 LLM（Claude Opus 4.1、Gemini 2.5 Pro、GPT-5）生成候选标签 → 人工筛选 → 80 个初始标签 → 合并为 16 个核心类别
  2. 标签分配阶段: 2 位标注员独立标注 332 个 Claude Code 文件 → 80.3% 一致率 → 第 3 位标注员调解分歧 → 最终 2,069 个标签分配

RQ4: 自动分类方法

  • 任务: 多标签分类（16 个类别）
  • 模型: GPT-5
  • 输入: 完整 ACF 内容 + 每个类别的描述和示例
  • 评估: Precision / Recall / F1-score（per-category + micro average）

关键公式

公式1: 效应量判断标准

$$ \text{Effect size} = \begin{cases} \text{negligible}, & \text{if } |d| \leq 0.147 \\ \text{small}, & \text{if } 0.147 < |d| \leq 0.33 \\ \text{medium}, & \text{if } 0.33 < |d| \leq 0.474 \\ \text{large}, & \text{if } 0.474 < |d| \leq 1 \end{cases} $$

含义: 用 Cliff's delta $d$ 量化两组样本之间差异的实际显著性，补充 Mann-Whitney U Test 的统计显著性判断

符号说明: - $d$: Cliff's delta 值，范围 $[-1, 1]$ - $|d|$: delta 的绝对值

公式2: Flesch Reading Ease

$$ FRE = 206.835 - 1.015 \times \frac{\text{total words}}{\text{total sentences}} - 84.6 \times \frac{\text{total syllables}}{\text{total words}} $$

含义: 衡量文本可读性，分数越高越容易阅读（0-100 范围）

符号说明: - $FRE$: Flesch Reading Ease 分数 - 低于 30 为 "Very Difficult"（大学毕业生水平） - 30-50 为 "Difficult"（大学水平）

批判性思考

优点

  1. 规模全面: 2,303 个文件、1,925 个仓库、3 种工具，是该领域迄今最大规模的实证研究
  2. 实践价值高: 16 类指令 taxonomy 直接可用于指导 ACF 编写和工具设计
  3. 方法严谨: 多标注员独立标注 + 调解机制，Mann-Whitney U + Cliff's delta 双重统计检验
  4. 洞察深刻: 揭示了 "功能性 vs 非功能性" 指令的显著失衡，对安全和性能有重要警示意义
  5. 可复现: 提供完整 replication package

局限性

  1. 仅分析根目录文件: 可能遗漏子目录中的 ACF（如 .github/copilot-instructions.md）
  2. 二值分类局限: 仅标记类别是否出现，未衡量指令的深度和质量
  3. 仅限开源项目: 企业内部的 ACF 实践可能有显著不同
  4. 人工标注仅覆盖 Claude Code: 332 个文件的标注结果用于推广到全部 2,303 个文件可能存在偏差

  2. 因果分析: 研究 ACF 内容质量对 Agent 生成代码质量的影响

一句话总结

首个大规模实证研究，分析 2,303 个 Agent 上下文文件（CLAUDE.md/AGENTS.md/copilot-instructions.md）的结构、维护模式与指令内容，揭示功能性指令主导而安全/性能等非功能性需求严重缺失的现状。

核心贡献

  1. 首个大规模 Agent 上下文文件实证研究: 收集 1,925 个仓库中的 2,303 个 Agent 上下文文件（ACF），覆盖 Claude Code、OpenAI Codex、GitHub Copilot 三大工具
  2. 16 类指令分类体系: 通过人工标注构建 Agent 上下文文件的指令分类 taxonomy，发现功能性指令（Build and Run 62.3%、Implementation Details 69.9%）远多于非功能性需求（Security 14.5%、Performance 14.5%）
  3. 自动分类可行性验证: 使用 GPT-5 实现 0.79 F1-score 的自动分类，证明大规模监控 Agent 上下文文件的可行性

问题背景

要解决的问题

Agentic Coding 工具（如 Claude Code、OpenAI Codex、GitHub Copilot）依赖 Agent 上下文文件（ACF）来理解项目架构、遵循编码规范、执行构建测试。但目前缺乏关于这些文件结构、演化方式和实际内容的系统性实证证据。

现有方法的局限

  • 官方文档仅提供高层指导（如"描述架构和工作流"），开发者只能通过试错来设计这些文件
  • 已有研究主要关注 LLM 的模型能力、交互模式和即时提示，而非持久化的项目级上下文配置
  • 前序工作 (Chatlatanagulchai et al., 2025) 仅研究了 253 个 Claude Code 文件，范围有限

本文的动机

Agent 上下文文件作为一种新型软件工件（"READMEs for agents"），在 Agentic Coding 生态中扮演关键角色，但学术界对其缺乏基本的经验性认知。本文旨在通过大规模实证分析填补这一空白。

方法详解

研究设计

本文围绕四个研究问题（RQ）展开：

  • RQ1: Agent 上下文文件的特征（大小、可读性、结构）是什么？
  • RQ2: 开发者维护 Agent 上下文文件的频率如何？
  • RQ3: Agent 上下文文件包含哪些指令？
  • RQ4: 能否自动分类 Agent 上下文文件中的指令？

数据收集

数据来源: AIDev 数据集 (Li et al., 2025b)，筛选 GitHub Stars ≥ 5 的 8,370 个仓库

文件检索: 通过 GitHub API 扫描仓库根目录，按官方命名规范检索： - CLAUDE.md → Claude Code（922 个） - AGENTS.md → OpenAI Codex（694 个） - copilot-instructions.md → GitHub Copilot（687 个） - 总计: 2,303 个文件来自 1,925 个仓库

RQ1: 特征分析方法

  • 大小: 正则表达式 \w+ 匹配单词数
  • 可读性: FRE 指标（越高越易读）
  • 结构: 统计 Markdown 标题层级（H1-H5）分布
  • 统计检验: Mann-Whitney U Test + Cliff's Delta 效应量

RQ2: 维护模式分析

  • 提取所有修改 ACF 的 commit 历史
  • 统计 commit 数量、时间间隔、增删行数
  • 总计分析 5,655（Claude Code）+ 2,767（Codex）+ 2,237（Copilot）= 10,659 次 commit

RQ3: 内容分类方法

两阶段人工标注:

  1. 标签创建阶段: 提取 H1/H2 标题 → 3 个 LLM（Claude Opus 4.1、Gemini 2.5 Pro、GPT-5）生成候选标签 → 人工筛选 → 80 个初始标签 → 合并为 16 个核心类别
  2. 标签分配阶段: 2 位标注员独立标注 332 个 Claude Code 文件 → 80.3% 一致率 → 第 3 位标注员调解分歧 → 最终 2,069 个标签分配

RQ4: 自动分类方法

  • 任务: 多标签分类（16 个类别）
  • 模型: GPT-5
  • 输入: 完整 ACF 内容 + 每个类别的描述和示例
  • 评估: Precision / Recall / F1-score（per-category + micro average）

关键公式

公式1: 效应量判断标准

$$ \text{Effect size} = \begin{cases} \text{negligible}, & \text{if } |d| \leq 0.147 \\ \text{small}, & \text{if } 0.147 < |d| \leq 0.33 \\ \text{medium}, & \text{if } 0.33 < |d| \leq 0.474 \\ \text{large}, & \text{if } 0.474 < |d| \leq 1 \end{cases} $$

含义: 用 Cliff's delta $d$ 量化两组样本之间差异的实际显著性，补充 Mann-Whitney U Test 的统计显著性判断

符号说明: - $d$: Cliff's delta 值，范围 $[-1, 1]$ - $|d|$: delta 的绝对值

公式2: Flesch Reading Ease

$$ FRE = 206.835 - 1.015 \times \frac{\text{total words}}{\text{total sentences}} - 84.6 \times \frac{\text{total syllables}}{\text{total words}} $$

含义: 衡量文本可读性，分数越高越容易阅读（0-100 范围）

符号说明: - $FRE$: Flesch Reading Ease 分数 - 低于 30 为 "Very Difficult"（大学毕业生水平） - 30-50 为 "Difficult"（大学水平）

批判性思考

优点

  1. 规模全面: 2,303 个文件、1,925 个仓库、3 种工具，是该领域迄今最大规模的实证研究
  2. 实践价值高: 16 类指令 taxonomy 直接可用于指导 ACF 编写和工具设计
  3. 方法严谨: 多标注员独立标注 + 调解机制，Mann-Whitney U + Cliff's delta 双重统计检验
  4. 洞察深刻: 揭示了 "功能性 vs 非功能性" 指令的显著失衡，对安全和性能有重要警示意义
  5. 可复现: 提供完整 replication package

局限性

  1. 仅分析根目录文件: 可能遗漏子目录中的 ACF（如 .github/copilot-instructions.md）
  2. 二值分类局限: 仅标记类别是否出现，未衡量指令的深度和质量
  3. 仅限开源项目: 企业内部的 ACF 实践可能有显著不同
  4. 人工标注仅覆盖 Claude Code: 332 个文件的标注结果用于推广到全部 2,303 个文件可能存在偏差

潜在改进方向

  1. 纵向追踪研究: 分析 ACF 与代码变更的 co-evolution 关系
  2. 因果分析: 研究 ACF 内容质量对 Agent 生成代码质量的影响
  3. 模板设计: 基于 16 类 taxonomy 设计标准化 ACF 模板
  4. 非功能性需求检测: 开发 CI 集成工具自动检测 ACF 中缺失的 Security/Performance 指令
